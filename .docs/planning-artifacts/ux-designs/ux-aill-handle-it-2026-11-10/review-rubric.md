# Spine Pair Review — AI'll handle it

## Overall verdict
The pair is a usable contract. Every colour token has a hex value (light only, which decision D justifies), and all 12 stated contrast ratios recompute exactly. The 30 component names match one to one across DESIGN.md › Components and EXPERIENCE.md › Component Patterns. All six UJ titles are taken verbatim from the PRD, and every memlog decision has landed in a spine. Two high-impact gaps remain before stories can be written. First, the committed hero tokens most likely break FR-7's "no scrolling on a phone" promise. Second, the position of the FR-18 arrival step is still open. Neither is critical. A handful of medium component and token gaps also remain: focus on the primary button, colours for status tags, the consent block, and the admin overview table.

## 1. Flow coverage — adequate
Checked: UJ-1 to UJ-6 from the PRD (§4), plus the v1 guest-flow FRs the flows depend on (FR-7, FR-13 to FR-23, FR-34 to FR-38, FR-41 to FR-43). All six UJs have a Key Flow with a named protagonist, numbered steps, a **Climax** beat and a failure path. The memlog override on the UJ-1 quality bar is applied.
### Findings
- **high** UJ-1 step 1 and the FR-7 Hero panel rule promise that names, date, place, invited names, "Barnefritt bryllup", deadline and the button are all visible without scrolling. The committed tokens most likely do not fit. At 360px wide the content box is about 292px (gutter 16 + hero inline padding 18 on each side). Image 17 (1695×928) is then about 160px tall. Adding the nav row (one or two lines at ≥44px), hero padding 30px, seal 96px, names 46px×1.2, invites, date, place, invited, child-free and deadline lines (about 30px each), and the 52px button gives about 670px or more, against roughly 560px of visible viewport at 360×640. This is left as Open Question 1 with no committed rule (EXPERIENCE › Component Patterns › Hero panel; Key Flows › UJ-1 step 1; Open Questions 1; DESIGN › Layout & Spacing front-page order). *Fix:* commit a budget now. Either cap the illustration height (for example `hero-illustration.maxHeight` ≤ 110px at narrow widths), let the seal shrink at 320–360px, or move the nav words below the hero or onto one line. Then verify with a 360×640 render before the stories are written.
- **high** FR-18 (expected arrival, a v1 guest-flow requirement) has no step position. The step order in Interaction Primitives skips it, and it is listed as open (EXPERIENCE › Interaction Primitives › Form step order; Open Questions 3 and 5). Form-step stories, the "Steg n av m" count and the check-answers grouping all depend on it. *Fix:* decide the position with Rikke (for example per person together with days, or as its own step before the hike), and record the fixed choices including "Vet ikke".
- **medium** FR-14 defines two steps: first who is coming, then "whole weekend?" with days per person. The memlog and EXPERIENCE make it one step: "who is coming and which days (FR-14)". The DESIGN example "Steg 2 av 6" means a different count depending on which reading is used (EXPERIENCE › Interaction Primitives; DESIGN › Components › Progress line; PRD FR-14). *Fix:* state explicitly whether step 1 is one screen or two, and update the progress-line example to match.
- **low** The PRD UJ-2 coda (the couple sees "Endret", pays Arild back and registers the refund so the balance is zero) has no flow beat. UJ-5 covers only received payments (EXPERIENCE › Key Flows › UJ-2, UJ-5). *Fix:* add a refund step to UJ-5 or a closing line to UJ-2 that points to A9.

## 2. Token completeness — adequate
Checked: all 17 `colors`, 13 `typography`, 3 `rounded` and 17 `spacing` tokens, 21 frontmatter components, and every `{path.to.token}` reference in both spines. All references resolve, and every colour has a hex value. There are no dark pairs, which is justified by memlog decision D ("light only"). The 12 contrast pairs recompute to the stated values (9.35, 10.61, 5.50, 8.08, 4.95, 8.86, 10.49, 6.64, 6.16, 5.67, 5.50 and 4.52:1).
### Findings
- **medium** The focus ring on cream is `focus-on-panel` `#344628`, which is the same value as the primary button fill `green-dark`. The 3px ring therefore merges with the button (1.00:1) unless there is an offset, and no offset is specified (DESIGN › Colors `focus-on-panel`; `components.button-primary`; EXPERIENCE › Accessibility Floor). *Fix:* add a `focus-offset` spacing token (for example 2–3px, so the cream panel shows between button and ring) and state it in Components › Primary button.
- **medium** The status tag says "outlined text label in the state colour", but nothing maps the payment statuses ("Ingenting å betale", "Ikke betalt", "Delbetalt, 300 kr mangler", "Betalt", "Skal ha tilbake 200 kr") or "Endret" to `success`, `warning`, `error` or `ink`. Only "Stemmer ikke" → `error` is given (DESIGN › Components › Status tag; EXPERIENCE › Component Patterns › Status tag). *Fix:* add a status → colour → icon table.
- **low** No visual tokens for the busy state ("Sender …", the button ignores repeat taps) or for hover/pressed on the secondary button, destructive button and text links. Only `green-dark-hover` exists (DESIGN frontmatter `components`). *Fix:* state whether busy buttons keep their colours, and give hover treatments for the remaining interactive components.
- **low** `rounded.none` is defined but never used. Prose gives choice boxes `{rounded.md}`, but `components.choice-control` has no radius, and the radio button is round (DESIGN frontmatter; › Shapes). *Fix:* remove `none` or use it, and add `radius` to `choice-control`.

## 3. Component coverage — adequate
Checked: every component name across both spines. All 30 rows in DESIGN › Components have a matching row in EXPERIENCE › Component Patterns with real behavioural rules. Gaps are components that are used but not named.
### Findings
- **medium** "One per screen" for the primary button conflicts with G2. The front page has the RSVP button in the hero and again in its own bottom panel (FR-8). Once the guest has answered, the status block adds a second "Se eller endre svar" primary button next to the hero button that becomes "Se eller endre svar" (FR-37) (DESIGN › Components › Primary button; EXPERIENCE › Component Patterns › Primary button and Status block). *Fix:* reword the rule as "one distinct primary action per screen; repeats of the same action allowed". Decide whether the hero button or the status block carries "Se eller endre svar" once the guest has answered.
- **medium** The consent block has no component row in either spine. It holds the purpose and recipients text before the choice, a Yes/No that starts unanswered, the "Jeg bekrefter at Marie vet om dette og er enig" confirmation, and the withdrawal entry. It is described only in prose, and this is the most sensitive control in the product (EXPERIENCE › Consent & Privacy UX; FR-26 to FR-28). *Fix:* add a "Consent block" row to both Components tables: visual (panel section, text order, choice control) and behavioural (starts unanswered, never blocks sending, confirmation shown only for others).
- **medium** Admin has no component for the A4 full overview (table on PC, stacked rows on phone, unanswered households "stand out", mismatch and "Endret" markers) or for the admin nav row. EXPERIENCE says "same word-row pattern", but DESIGN's Nav words are cream text on `page-green` with no admin variant (EXPERIENCE › IA A4 and admin navigation; › Responsive & Platform; DESIGN › Layout & Spacing › Admin). *Fix:* add "Overview row / table" and an admin nav variant (or say explicitly that admin reuses Nav words on green).
- **low** Several pieces are named in IA or states but not as components: the last-updated header (G4b), the typed-confirmation input for tier 3, the multi-line question field (G10) and the admin search field (A6). *Fix:* name them as variants of Text field or Notice in both tables.
