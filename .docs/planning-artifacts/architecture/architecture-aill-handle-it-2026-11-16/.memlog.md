- (decision) Paradigm: functional core, imperative shell inside one server-rendered Django monolith. Pure rule module (no Django imports, no database): totals, counts, payment status, deadline lock, which questions apply (FR-15, FR-33, FR-41-42, FR-60-61, FR-73-75). Services are the only code that writes to the database, each write in one transaction. Views and templates are thin: read via services/selectors, render HTML. Why: NFR-2 and FR-69 make the counting rules the riskiest logic; keeping them pure lets the expected-results tests call them directly and stops two screens counting differently. Prevents: the guest page and the admin summary computing totals or counts in different places.
- (decision) Django apps: 'wedding' owns all models, the rule module, services and management commands (seed test data, create admin users); 'guests' holds the guest-facing views/templates reached by personal link; 'dashboard' holds the couple's and helpers' admin area. guests and dashboard depend on wedding, never on each other. Django's built-in admin site is not the couple's UI (the UX designed its own admin pages); it may stay off. Prevents: two owners of the same model, and guest code importing admin code or the reverse.
- (decision) D14 link codes: stored in plain form (unique, indexed), not hashed. Why: FR-51 requires the couple to copy a guest's link at any time and FR-52 [2027] builds the invitation message from it; a hashed code can only be shown once, at creation. Codes come from Python's secrets module with 128 bits of randomness (secrets.token_urlsafe(16), 22 URL-safe characters, NFR-4, NFR-1). Risk accepted: anyone with the database file could open guest pages; mitigated by restricted server access, encrypted backups (PRD 3.2) and FR-53 (deactivate and re-issue one guest's link).

- (decision) Guest RSVP form (closes UX open question 4): server-rendered steps. Each step is a normal HTML form POSTed to the server, which validates it, works out the next applicable step and the running total with the rule module, and redirects (POST-redirect-GET). Guest pages and all form steps work without JavaScript in v1; scripts only enhance (FR-20 leave warning, small conveniences). 'Read more' inside a step uses <details>, no script. Why: one place decides which questions apply and what things cost, and old phones and in-app browsers get plain HTML. Prevents: a JS copy of the rules drifting from the server's.
- (decision) Unsent answer (draft, FR-78): kept on the guest's device in a signed, compressed cookie (Django signing), scoped to that guest's link path so two links on one phone never mix, expiring at the RSVP deadline, and cleared on 'Send answer' and 'Begynn på nytt'. Nothing about an unsent answer is written to the database; the first database write is 'Send answer'. Why: FR-78 without scripts, and no allergy data on the server before consent (FR-26, FR-28). Constraint: a cookie holds at most 4 KB, so the allergy note has a maximum length and a test covers the largest household. Prevents: one unit keeping drafts in the database while another keeps them in localStorage.

- (decision) UX open question 5 closed (Rikke chose A): admin sessions expire after 20 hours without activity, sliding (every request renews it; Django SESSION_COOKIE_AGE plus SESSION_SAVE_EVERY_REQUEST). No expiry warning and no restore of unsaved input after re-login, since expiry during use is practically impossible at 20 hours. A visible 'Logg ut' button on every admin page. Applies to the couple and helpers alike.
- (decision) Concurrent household answers (FR-38): each household's sent answer has a revision number. The form remembers the revision it started from; 'Send answer' is accepted only if the revision is unchanged, otherwise the guest sees the other answer (who, when, what differs) before sending again. The check-and-write happens inside one IMMEDIATE SQLite transaction. Prevents: last-write-wins in one unit while another assumes merge.
- (decision) SQLite settings: WAL journal and busy timeout via OPTIONS init_command, transaction_mode IMMEDIATE (Django 5.1+), short transactions, no ATOMIC_REQUESTS; writes wrap transaction.atomic in services.
- (decision) Stored vs derived (NFR-2): stored are the facts people enter (guests, households, per-person answers, consents, 'I have paid' reports, registered payments and refunds, settings incl. prices and deadline, the 'Changed' marker and 'Needs attention' handled marks). Never stored: totals, counts, payment status, lock state, match/mismatch of a payment report; these are always computed by the rule module from stored facts and current settings.
- (decision) Money is whole kroner as integers everywhere (NFR-2); no floats or decimals for amounts.
- (decision) Time: USE_TZ on, stored in UTC, shown in Europe/Oslo (FR-41). The deadline is stored as a date; one rule-module function decides whether a moment is after 23:59:59 Oslo time on that date. Every lock check (guest views, services) calls that function.
- (decision) Access: guests have no Django user; a request is a guest request only through a valid, active link code, resolved by one function. Admin users are Django users with exactly one role, couple or helper.
