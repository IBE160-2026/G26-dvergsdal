- (decision) Paradigm: functional core, imperative shell inside one server-rendered Django monolith. Pure rule module (no Django imports, no database): totals, counts, payment status, deadline lock, which questions apply (FR-15, FR-33, FR-41-42, FR-60-61, FR-73-75). Services are the only code that writes to the database, each write in one transaction. Views and templates are thin: read via services/selectors, render HTML. Why: NFR-2 and FR-69 make the counting rules the riskiest logic; keeping them pure lets the expected-results tests call them directly and stops two screens counting differently. Prevents: the guest page and the admin summary computing totals or counts in different places.
- (decision) Django apps: 'wedding' owns all models, the rule module, services and management commands (seed test data, create admin users); 'guests' holds the guest-facing views/templates reached by personal link; 'dashboard' holds the couple's and helpers' admin area. guests and dashboard depend on wedding, never on each other. Django's built-in admin site is not the couple's UI (the UX designed its own admin pages); it may stay off. Prevents: two owners of the same model, and guest code importing admin code or the reverse.
