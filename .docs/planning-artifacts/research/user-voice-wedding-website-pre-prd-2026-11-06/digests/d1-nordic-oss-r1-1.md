## Data-model patterns from open-source projects (your synthesis)

- **Household is the unit of invitation, the person is the unit of answer.** Both well-documented projects use `Party`/`Invite` (household) 1–N `Guest`. The token or secret link belongs to the household; attendance and meal choice belong to each guest.
- **Token on the household.** czue uses a random 32-char hex `invitation_id` (unique, indexed) in the URL. git-hitched uses signed, expiring links plus email lookup. Neither uses logins for guests.
- **Tri-state attendance.** Both use nullable boolean (`null` = not answered yet). The admin "not responded" list comes from this.
- **Multi-event = join tables.** git-hitched's `EventInvite` (which household is invited to which event) and `RSVP(guest, event)` map directly to a three-day weekend (Friday dinner, wedding day, Sunday brunch). czue only has a single `rehearsal_dinner` flag, which does not scale.
- **Meals as an enum per guest** with a `tbd`/null state and free-text dietary notes. Children are flagged (`is_child`, age) for counts and pricing.
- **Money stored in integer cents** (`amount_in_cents`) with a status lifecycle (pending/confirmed/refunded).
- **Admin = dashboard of aggregates + CRUD + CSV import/export.** Guests are bulk-loaded from a spreadsheet.

Suggested entity sketch for this project: `Household(token, name, notes, responded_at)` 1–N `Guest(name, is_child/age, dietary_notes)`; `Event/Meal(day, name, price_nok, child_price)`; `Attendance/MealOrder(guest, event, attending|null)`; `Cabin/Accommodation(name, capacity, price)` N–1 assignment per household or guest; the amount owed is *derived* from orders and accommodation, never stored as free text.

## Patterns worth borrowing / pitfalls

- Borrow: one secret link per household, with names pre-filled (czue). Per-guest per-event RSVP (git-hitched). Admin list of "not answered" and "missing meal" (czue). CSV import of the guest list.
- Borrow: a deadline-driven flow. Norwegian guidance points to a deadline about 1 month before the wedding (2024 source). For speeches, the Swedish example closes speech sign-up 2 weeks before.
- Borrow: a speech/performance sign-up that only the toastmaster sees (name, relation, type, duration ~5 min, tech needs, preferred timing). The Swedish example explicitly hides it from the couple.
- Pitfall: payment. git-hitched builds Stripe in, which is complexity this project avoids by showing "amount owed + bank account/Vipps info". Store amounts as integers (øre or whole NOK) and compute totals rather than storing them.
- Pitfall: guest-paid costs are socially sensitive in Norway (Klikk.no "tabber"). Show prices clearly and early, without surprises, and in a friendly tone.
- Pitfall: no project found has i18n or Norwegian UI. Norwegian text and NOK formatting must be built from scratch.
- Pitfall: czue's hard-coded single extra event (`rehearsal_dinner` bool) shows what goes wrong if multiple days are modelled as flags.
- Leave out (as the OSS projects do): guest accounts and logins, seating charts (optional), and email open-tracking (a privacy concern under GDPR).

## Looked for but could not find

- **No Norwegian-built wedding RSVP service** with households, meal choices or payment info came up. Results were dominated by planning.wedding (multi-language vendor) and international services (Zola, Joy, WedSites). This is thin data. The finding is that Norwegian couples likely use international tools, generic builders (Wix/Canva) or Google Forms/Excel, but I have no survey data on how common each is.
- **No Norwegian source on guests paying for meals** at multi-day weddings. Evidence covers only accommodation (guests pay, couple negotiates a rate). Paid meals chosen by guests appear to be uncommon or at least undocumented online.
- **No Norwegian source on "talelister"** or the formal process of signing up to give a speech via the toastmaster. Only the Norwegian speech order (Klikk.no) and a Swedish form example were found.
- **No authoritative Norwegian RSVP-deadline norm.** The only Norwegian-language source is a 2024 Polish vendor blog (about 1 month before).
- No Facebook-event usage data for weddings.
- No Swedish source explicitly defining OSA ("om svar anhålles"). Its meaning is inferred from usage in forms.
